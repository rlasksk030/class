# 일반 학급 실환경 비게시 검증 — 실제 입력·첨부·원본 대조 PASS

기준 `6890b961527ff4a1f76fedbdd2d9126db2e44341` 및 이번 변경. 기존 A/B/C·실제 앱 완주 성공 게시물은 조회·재게시·변경하지 않았다. 운영 잠금, 정식 버전, 하이클래스, 옥구초 배포 채널은 변경하지 않았다.

최초 확인 시에는 학교종이 작성창을 유지하고 기존 내용 보존 여부를 사용자에게 물었다. 이후 사용자가 “빈 작성 화면이며 기존 미완료 글·첨부 없음”이라고 확인하여 위 정정을 진행했다. 불일치 원인은 학급 이름 파서가 아니라 저장된 앱 설정이므로 파서를 완화하거나 `gradeClass=true`로 바꾸지 않았다.

후속 실행 코드는 `edcda76fddc865b9109408077186087b231448fe`다. 같은 별도 개발 프로필로 앱을 정상 종료·재실행했고, 새 학급 키에서 학교종이를 선택해 앱 소유 서비스 창을 열었다. 학급별 로그인 공간을 분리하므로 기존 1학년 3반 공간의 쿠키·인증정보·승인 기록은 2반으로 복사하지 않았다. 협조 교사가 새 창에서 직접 로그인한 뒤 일반 학급의 알림장을 열었다.

실제 작성하기를 열자 날짜형 제목이 들어 있었다. 첫 비게시 검사는 `blank-composer / existing-content`에서 멈췄고 제목·본문·첨부는 모두 NOT RUN이었다. 사용자가 이 제목은 사이트의 자동 기본값이며 본문·첨부는 없다고 확인한 뒤, 화면에서 확인된 해당 날짜 제목만 선택하여 지웠다. 기존 글 보호를 약화하거나 날짜 제목을 일괄 덮어쓰는 코드는 추가하지 않았다. 따라서 이 결과는 기본 날짜 제목 정리까지 무인 자동화됐다는 뜻이 아니다.

그 후 같은 앱 검사 버튼에서 현재 학급·고정된 가상 자료·비게시 범위 확인창을 거쳐 **context → blankComposer → teacherConsent → title → body → upload → original → finalContext** 모두 실제 서비스에서 통과했다. 앱에도 ‘비게시 제목·본문·사진 입력 및 원본 대조 완료’가 표시됐고 운영 등록 버튼은 비활성 상태를 유지했다. 원본 SHA-256: `4b710117b406cde8188ac5cd00c8c2853f73c11815a073463a9ce142ffb92c53` (79 bytes, 1장).

가상 문구와 첨부가 있는 서비스 작성창은 미게시 상태로 유지했다. 앱 초안과 기존 글은 변경·삭제하지 않았다. 보내기·예약·임시저장 및 수신대상 변경은 실행하지 않았으며, 서버의 내부 임시 업로드 보관 정책까지 검증했다는 뜻은 아니다. 일반 학급의 실제 게시 권한/총 수신 인원/고유 신원은 여전히 미검증이다. 이 비게시 결과를 게시 이력이나 운영 승인으로 저장하지 않았다.

## 변경 범위

- `schoolbell-recipients.cjs`, `schoolbell-live-context.cjs`, `schoolbell.cjs`: 현재 화면의 역할별 선택/변경 가능 상태를 제한된 boolean과 표시 행 수로 전달한다. 이름·연락처·수신대상 원문은 IPC/진단으로 전달하지 않는다. 전체 학생/보호자 수는 null, `recipientsVerified`는 false다.
- `schoolbell-nonpublishing.cjs`: 개발 시험 프로필에서 고정된 가상 제목·본문·PNG 한 장만 준비하는 별도 경로. 현재 문서/학급과 수신대상, 처음부터 빈 작성 화면, 교사 협조 확인을 요구한다. 기존 제목·본문·첨부, 학급/수신자 변경, 원본 불일치 및 예약 상태를 차단한다. 게시/예약/임시저장·이력 성공·앱 초안 초기화 경로가 없다.
- 기존 `schoolbell-observed-composer.cjs`의 제목/본문/파일 입력을 재사용한다. 새 가드가 동일한 본문 판독기를 사용하도록 읽기 전용 인자 하나만 추가했다. 보내기·커밋 비교 및 기존 게시 승인 규칙은 바꾸지 않았다.
- 앱 개발 검사 영역에 ‘일반 학급 비게시 입력·사진 검사’를 연결했다. main에서 현재 학급과 정확한 합성 자료를 표시해 확인한 경우만 진행하며, 기존 테스트 게시 승인은 폐기하고 재사용하지 않는다. 패키징된 운영 앱에서는 사용할 수 없다.
- 실제 서비스의 고유 계정/학교/학년도 검증과 사용자 확인을 구분한다. 비게시 검사 성공은 게시 권한, 공식 서비스 허용 또는 운영 활성화 증거가 아니다.

## 이번에 수행한 검사

- 수신대상/실제 UI 증거 관련 단위 검사 11개 통과: 기존 가림·중복 창 차단, 비어 있지 않은 표, 개인정보 미전달, 누락 상태를 확인했다.
- 비게시 처리기/기존 composer 관련 단위 검사 14개 통과. 최종 입력 증거와 예약 상태 사전 차단 보강 후 비게시 처리기 5개를 다시 확인했다.
- 격리된 Electron 검사 3개 통과: 기존 프레임워크 입력 이벤트와 줄바꿈·파일 전달, 확인 중 생긴 기존 글 보존, 수신대상 변경 후 입력/첨부 차단. HTTPS를 로컬로 차단한 합성 검사이며 실제 일반 학급 입력·업로드 PASS가 아니다.
- 변경한 main/preload/화면 스크립트 구문 및 diff 공백 검사 통과. 기존 전체 회귀·A/B/C·실게시 완주 시험은 반복하지 않았다.
- 후속 실환경 검사는 위 실행 커밋 그대로 진행했다. 소스 재수정·단위/전체 검사 재실행 없이 기본 제목 보호 차단과 실제 비게시 완료 결과를 각각 보존했다.

증거: [개인정보 없는 관찰/검사 결과](artifacts/2026-11-10-schoolbell-ordinary-nonpublishing/).

## 남은 조건과 다음 단계

1. 완료: 사용자 확인 후 빈 작성창을 정리하고 앱의 1학년 2반 설정을 실제 저장했다.
2. 완료: 교사가 2반 전용 앱 창에서 직접 로그인했다. 실제 학급/수신대상 재확인 후 승인된 합성 자료만 비게시 입력·첨부·원본 대조했다. 보내기/예약/임시저장은 각각 0회다.
3. 운영 BLOCKED: 서비스가 독립적으로 제공하는 학교·학년도·고유 교사 신원 및 게시 권한 근거, 실제 총 수신대상 범위 검증이 남았다. 화면 관찰·교사 확인을 서비스 검증 PASS로 승격하지 않는다.
4. 별도 Windows 베타 제작이 다음 우선 작업이다. 기존 [베타 배포 계획](2026-11-10-schoolbell-beta-distribution.md)의 별도 appId/userData/업데이트 격리 및 Windows 최소 설치 스모크가 먼저 필요하다. 이번에는 EXE·베타/정식 Release·업데이트를 배포하지 않았다. Windows 설치 검사는 사용자가 다음 날 학교에서 진행하기로 한 상태를 유지한다.
