# 학교종이 마지막 보내기 입력 수정

기준 `c1df74dc47559b4b4ee8b936289e5260ef0d1471`, PR #5 Draft, 운영 잠금 유지.

## 확인된 차이와 수정

기존 Electron 구현은 `send.click()`을 호출했다. 이 호출의 반환은 실제 게시 성공 증거가 아니며, 기존 실서비스 시험에서는 완료 화면 이동 및 새 서버 글이 없었다. 이전 A/B/C는 연결 브라우저의 실제 UI 클릭으로 성공했다. 서비스가 어떤 이벤트를 필수로 요구하는지는 아직 확인되지 않았다.

마지막 보내기에만 Electron의 실제 `mouseDown`/`mouseUp` 입력을 사용한다. 기존 입력·첨부·원본 검증은 재구현하지 않았다. DOM click fallback/자동 재시도는 없다. 소유 창의 초점을 확인하고 검증한 단일 버튼의 현재 위치·가림·상속된 비활성 상태를 검사한다. 각 native 이벤트에서 같은 대상, 본문 revision, 내용, 사진, 수신자, 발행 방식 및 만료된 검증 여부를 다시 대조한다. click 이벤트가 실제 trusted down/up 순서로 전달됐는지 확인하며, 그 결과도 게시 성공으로 처리하지 않는다.

전송 뒤 작성 화면·버튼 상태·표시 중 검증 오류/알림·완료 게시판 이동을 구조적 값과 정해진 메시지 종류만으로 기록한다. 임의 사이트 문구, 계정, 학급 식별정보는 진단 파일에 저장하지 않는다. 실제 완료 화면과 독립 서버 재조회·원본 검증이 성공해야 기존 성공 이력/변경 없는 초안 정리로 진행한다.

참고: [Electron sendInputEvent의 창 초점 조건](https://www.electronjs.org/docs/latest/api/web-contents#contentssendinputeventinputevent).

## 최초 구현 검증 (fcf76b9, 후속 실행 전 기록)

변경한 마지막 입력 경로만 격리된 Electron 화면에서 확인했다. DOM click과 trusted 마우스 이벤트 차이, 125% 확대에서 단일 전달, 재호출 차단, down/up 사이 본문 변경 차단, 가려진 버튼 및 상속 비활성 차단, 개인정보 없는 오류 진단을 확인했다. 6개 확인 통과. 첫 실행의 fixture 변수명 충돌 실패 기록도 보존했다. 기존 전체 검사/A/B/C 게시 시험을 반복하지 않았다.

실서비스 재시험 전 전체 게시물 조회: 4건, 동일 시험 제목 0건. 앱 자체 로그인 세션을 재사용했다. 현재 실제 앱에서 제목·본문·가상 PNG 1장 업로드 및 97 bytes 원본 해시 대조를 다시 통과하고 native 최종 확인창에 도달했다. 이 시점에는 새 보내기 방식이 아직 실서비스에서 실행되지 않았다. 이후 사용자가 같은 내용 1회 게시와 필수 게이트 통과 시 배포를 승인했으며, 그 실행 결과는 아래에 별도로 기록한다.

Actions 실행 요청 0회. 새 빌드·유료 자원·배포 없음. Windows 및 정식 운영 승인 상태는 이번 수정으로 바뀌지 않는다.

## 사용자 조건부 배포 승인 이후 첫 실행

동일 제목·본문·PNG 1장에 대한 명시적 사용자 승인으로 실행했다. 기존 native 확인창은 30분 시험 권한이 만료돼 게시 없이 취소했으며, 현재 학급/빈 대상과 서버 중복을 다시 확인했다.

실제 최종 실행은 `commitOnce`에서 `publication-unverified`로 중단됐다. trusted 클릭 전달 기록은 없고 정확한 내부 실패 단계는 당시 진단으로 확정할 수 없다. 이를 실제 게시 완료 또는 실제 클릭 성공으로 표시하지 않는다. 서버 전체 재조회는 4건/동일 제목 0건이었다. 자동 재클릭 없음. 초안·사진·불확실 시도 기록 보존.

이 실패 지점을 구분하기 위해 버튼 가림/상속 비활성/초점과 입력 전달 직전 진단을 추가했다. 보내기 단계 진입 후에는 시험용 서비스 창을 보존해 실제 오류 화면을 확인할 수 있게 했다. 진단 값은 boolean·개수·고정 분류만 저장하며, 계정/학급 식별정보/내용을 포함하지 않는다. 추가 입력 진단은 게시 전 준비 단계에서 읽을 수 있다.

**현재 정식 업데이트 게이트는 미충족이다.** 조건부 배포 승인을 실제 앱 등록 성공 또는 Windows PASS로 대체하지 않는다.

## 실제 가림 상태와 후속 수정

첫 실행 이후 게시 전 준비에서는 `upload-unverified`가 발생했다. 해당 시도에는 `commitOnce` 진입이 없었다. 준비 도중 기록된 보내기 버튼은 visible/enabled였지만 중심점의 실제 대상은 다른 DIV였고, 버튼을 맞히는 표본 좌표는 0개였다. 이 관측은 가림을 입증하지만 **최초 전송 실패의 내부 원인까지 확정하지는 않는다**.

다음 읽기 전용 진단에서는 합성 제목/본문만 입력하고 보내기를 누르지 않았다. 드롭다운을 닫았을 때와 즉시발행 드롭다운을 열었을 때 모두 중심점이 실제 보내기 버튼을 맞혔다. 따라서 발행 메뉴 자체가 항상 버튼을 가리는 것은 아니다. 이 진단에는 사진을 선택하지 않았으며, 원본 확인 기능의 attachment-list 차단을 사진 업로드 회귀 실패로 세지 않는다.

후속 수정은 전송 전에 버튼 위치와 가림을 두 번 연속 확인할 때까지 최대 2초 기다린다. 기다리는 동안 창/권한을 다시 확인하고, 준비되면 기존 최종 증거와 매 native 이벤트 guard를 그대로 수행한다. 시간 초과 시 입력하지 않는다. 이미 전송한 클릭을 재시도하지 않는다. 초점/전달 직전/가림 실패를 구분하는 진단을 추가했으며 시험 프로필의 편집 창은 실패 후에도 보존한다. 입력·첨부 자체는 재구현하지 않았다.

이 수정의 로컬 Electron 확인은 7개 통과했다. 기존 6개 경계에 ‘닫히는 가림 화면이 사라진 뒤 단 한 번 전달’을 추가했다. 관련 composer 단위 검사 7개도 통과했다. 이 결과는 실서비스 성공을 대체하지 않는다. 전체 검사는 변경 없이 반복하지 않았다.

현재 실행 중인 앱에는 최신 대기 수정이 아직 반영되지 않았다. 미게시 합성 진단 작성창의 페이지 이탈 확인이 떠 있으며, 정상 재시작을 위한 그 작성창 취소는 자동 승인 검토에서 차단됐다. 합성 문구와 97 bytes 원본은 로컬에 별도로 보존하고 재확인했다. 사용자에게 해당 진단 창 취소만 별도로 물었으며 **게시 승인 자체를 다시 요구하지 않았다**. 강제 종료나 다른 경로로 이 차단을 우회하지 않았다.

| 항목 | 이번 결과 |
|---|---|
| 앱 입력/사진 1장/게시 전 원본 대조 | 첫 실서비스 준비에서 확인 |
| 실제 보내기 → 서버 새 글 | FAIL: 최초 시도 publication-unverified, 전체 재조회 동일 제목 0건 |
| 새 버튼 대기 수정의 실서비스 검증 | BLOCKED: 수정 앱 재시작 전 |
| 게시 후 사진 원본/성공 이력/초안 초기화 | NOT RUN: 성공 게시물 없음. 초안/사진 보존 |
| 하이클래스 최종 전체 회귀 | NOT RUN: 관련 소스 변경 없음; 이전 PASS와 구분 |
| Windows 제품/설치/업데이트/재부팅 | NOT RUN: 환경 진단과 별도 |
| 전국용 운영 권한·수신자 경로 | 운영 잠금 유지, 시험 권한을 운영 허용으로 대체하지 않음 |
| 병합/신규 버전/Release/업데이트 채널 | NO GO: 필수 게이트 미충족, 수행하지 않음 |

새 유료 자원/계정/서비스 없음. GitHub Actions 요청 0회. 학생/학부모/계정/학급 식별정보나 세션은 저장소 증거에 포함하지 않는다.

## Windows 환경 재확인

기존 VM을 suspended에서 재개했고 CMD 및 `--current-user` 응답은 확인했다. 기존의 ‘VM이 전혀 응답하지 않음’을 이번 상태로 재사용하지 않는다. 게스트 프로세서 표시는 ARM64다. PATH, 표준 Node 설치 위치, Windows/사용자 임시 폴더, 사용자 영역과 기존 QA 폴더에서 실행 파일을 찾지 못했다. 이는 해당 검색 범위의 결과이며 다른 모든 위치에 Node가 없다는 증거는 아니다. 한국어 stderr를 UTF-8로 처리하던 호스트 진단의 decode 오류는 CP949 처리로 수정했다.

새 Node/제품 설치나 VM 생성은 하지 않았다. Windows x64 제품 실행·이전 버전 업데이트·데이터 보존·재부팅 검사는 아직 NOT RUN이다. 진단 후 VM을 기존 suspended 상태로 복구하고 확인했다. 환경 확인 결과를 제품 테스트 PASS 또는 FAIL로 대신하지 않는다.

## 작성창 취소 승인 이후

[정상 재실행 및 비게시 검증 후속 기록](2026-11-10-schoolbell-restart.md)에서 작성창 취소/재시작 차단은 해결됐다. 수정 앱의 실제 입력 준비는 본문 입력 직후 `context-unverified`로 중단됐으며 새 보내기 단계는 NOT RUN이다. 이전 승인 대기 기록을 현재 차단 사유로 재사용하지 않는다.
